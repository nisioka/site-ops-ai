# ルーティン（クラウドでの定期実行）

週次でサイト診断を回す設定。**サイトのリポジトリごとに1本ずつ**登録する。

## 仕組み

Claude のスケジュール実行（クラウドエージェント）を、対象サイトのリポジトリに対して登録する。
起動したセッションが `site-ops` スキルに従って収集・判断し、必要に応じて PR / Issue を作る。

判断は Claude のセッション内で行われるため、Claude API の従量課金は発生しない。

## 事前に用意するもの

### リポジトリ側

- `.claude/site-ops.yml`（サイト設定）
- `.claude/skills/site-ops/SKILL.md`（スキル。プラグインで入れる場合は不要）

### 実行環境の Secret

| 変数 | 値 | 必須 |
| --- | --- | --- |
| `GOOGLE_SERVICE_ACCOUNT_JSON` | サービスアカウント鍵 JSON の**本体**（または base64 文字列） | 必須 |
| `PSI_API_KEY` | PageSpeed Insights API キー | 任意 |

クラウド実行では鍵ファイルを置けないため、`GOOGLE_APPLICATION_CREDENTIALS`（パス指定）ではなく
`GOOGLE_SERVICE_ACCOUNT_JSON`（本体）を使う。改行やクォートで壊れる環境なら base64 を渡す。

```bash
# GNU/BSD どちらでも動く形（macOS の base64 に -w は無い）
base64 < service-account.json | tr -d '\n'   # これを Secret に貼る
```

GitHub への書き込み（PR / Issue 作成）はエージェント環境の GitHub 連携を使う。
別途 PAT を用意する必要はない。

## 登録

`/schedule` で対象リポジトリに対してスケジュール実行を作成し、発火プロンプトに以下を入れる。

```text
site-ops スキルに従って週次のサイト診断を実行してください。
計測データを収集し、このリポジトリのコードと突き合わせて判断すること。
コードで直せて検証できるものは PR、人間の判断が要るものは Issue、
変化がノイズの範囲またはデータ不足なら改善提案は作らず、理由を報告してください。
数値はスナップショットから引用し、推測で埋めないこと。
```

## 実行間隔

週次・**毎週月曜 09:00 (JST)** を目安にする。

- GSC のデータ反映は2〜3日遅れる。CLI は終端日を3日遡らせて集計しているため、
  月曜実行なら確定データが揃う
- cron: JST 固定なら `0 9 * * 1`、UTC なら `0 0 * * 1`

日次にはしない。週次の変動ですら母数が小さいと判断できないため、日次では材料が足りない。

## 段階導入

1. まず手元で `npx -y github:nisioka/site-ops-ai#v0.2.0 collect` を実行し、要約の内容を確認する
2. 1リポジトリだけスケジュール登録し、数週間ぶんの PR / Issue の質を見る
3. 問題なければ残りのリポジトリへ広げる

private リポジトリでは `.site-ops/` にスナップショットが数週分たまるまで、トレンド判断が
できないため提案の質は上がりきらない。最初の数回は改善提案なしで終わるのが正常。

public リポジトリではスナップショットをコミットしない（計測データを公開しないため。
[README の「スナップショットの公開範囲」](../README.md#3-スナップショットの公開範囲を決める)を参照）。
毎回そのときの1週分だけで判断することになる。
